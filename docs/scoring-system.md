# Scoring System v4 — Two-Coordinate KTC Arbitrage

Chicago Dynasty (Sleeper league `1312124603224555520`, 12-team 1QB dynasty, full PPR; my team: bengramling, roster_id 4). This spec supersedes v2 (never implemented) and v1 (the running engine at the time of writing). It is THE contract: the engine implements it exactly, and its invariants are the test suite.

## 0. Design principles (user-locked, 2026-07-27)

1. **Simple.** The model fits on an index card. Anything that doesn't earn its place is out.
2. **Only reliably computable inputs.** Every number in the scoring path is KTC price data, roster arithmetic, or a fact about a completed transaction. No estimated probabilities, no simulated opponent utilities, no invented constants. (KTC itself "is really a loose estimate" — the user's words — so no precision machinery gets built on top of it.)
3. **Rational roster management is assumed**, for every team including mine. Roster counts and pending cuts are housekeeping, not signals: "just because somebody is over the roster limit, that does not mean that they are a seller."
4. **Strategy**: wealth arbitrage between postures. Sell veteran players to teams that want to win now; buy players from / sell picks to teams that are rebuilding. Every trade pairing ends roster-neutral. Deadlines are execution logistics, not score inputs.

## 2. The score — two objective coordinates, no blend (v4)

The user's ask, verbatim: "a deterministic way to value one of these spreads. I want to know 'Will this trade make my team better and by how much?' If possible, I want an objective calculation that works in all cases." v4 delivers exactly the objectivity that is mathematically available — and no more.

Every trade's effect on a side decomposes into two parameter-free numbers, both pure roster arithmetic on KTC face values:

```
ΔS = change in STARTER value: the max-Σv legal lineup (QB / 2 RB / 3 WR / TE / 2 FLEX)
     solved over active + taxi players at raw KTC v, after minus before
     (taxi startable — promote-anytime, §8; IR and empty slots = 0;
      for a pair, BOTH legs applied together — legs interact through the lineup)
ΔF = change in TOTAL FACE owned: Σ v(in) − Σ v(out), players and picks alike
     (picks at tranche; additive across legs; conserved per leg — §11.1)
```

Any single-number ledger is `ΔW(δ) = ΔS + δ·(ΔF − ΔS)` for some stored-value preference δ — and **δ is a time preference (win-now ↔ win-later), not a measurable fact**. It is bounded for every rational manager: free disposal ⇒ δ ≥ 0; a starter is a stored asset plus the free option of fielding him ⇒ δ ≤ 1. `ΔW(δ)` is linear in δ, so its value across ALL rational preferences ranges exactly between its endpoints: `ΔS` (at δ = 0) and `ΔF` (at δ = 1). Therefore:

- **Verdict (objective, works in all cases):** a spread is better for EVERY rational preference iff `ΔS ≥ 0 AND ΔF ≥ 0`, at least one strict. This is the user's strategy statement formalized — "increase my team's strength by … capturing edge on both legs." Face-only readmits the two-QB disaster; starter-only readmits bench-stripping; the two coordinates police each other. The board recommends ONLY objectively-good spreads.
- **Magnitude (objective):** the gain is the interval `[floor, ceiling] = [min(ΔS, ΔF), max(ΔS, ΔF)]`. The **floor is the guaranteed gain** — the worst case over every rational preference. A single point inside the interval would require choosing a δ; none is chosen, anywhere.
- **Ranking (objective, maximin):** guaranteed floor descending; ceiling descending as tie-break; deterministic ids last. No preference parameter exists in the system.
- **Preference trades are labeled, not scored.** A spread failing one coordinate is not "bad" — it is preference-dependent, and carries an objective breakeven `δ* = ΔS / (ΔS − ΔF)`: the QB case below is good exactly for δ > 0.5 (a rebuilder's trade). The CLI reports the breakeven for any scored proposal; the board never recommends these.
- **The two user QB cases (locked 2026-07-28) restate as verdicts:** 8,000 + 4,000 → 7,000 + 6,000 is (ΔS −1,000, ΔF +1,000) — NOT objectively good, breakeven δ = 0.5. A 5,000 → 6,000 backup upgrade is (ΔS 0, ΔF +1,000) — objectively good, gain 0 to +1,000 (floor 0 ranks it honestly low). A non-starter sold for a same-face pick is (0, ≈0) — the v3.4 reclassification exploit stays dead with no parameter needed.
- **Raw v only.** The S-solve is the greedy per-slot fill (exact for raw Σv), deterministic ties by KTC playerID asc. None of the league-tab lineup machinery — q insurance weights, availability multipliers, replacement values — enters the trade path (§11.2).
- **Per-side, both coordinates.** Each side's (ΔS, ΔF) is computed against its own roster. ΔF is exactly zero-sum across the parties of a leg (§11.1); ΔS is not — deployment differs by roster, which is why both sides of a good spread can genuinely gain.
- **Nothing else moves the score.** Not roster counts, not pending cuts, not deadlines, not probabilities, not the counterparty's internal valuation, and not KTC's consolidation adjustment (that prices trades in §3; it never values them). §11's regression invariants enforce each exclusion explicitly.
- A spread with `0 < floor < W_min = 150` carries a display-level noise note (inside KTC's own error bars), never hidden.

## 3. The fairness gate — "would they think it's fair?"

League-mates evaluate trades by checking KTC — the same site this system scrapes. The gate models exactly that check, with tolerances **measured from this league's ~33 completed trades**, not invented:

1. **Exact calculator band (v3.4).** Packages are compared exactly as KTC's own trade calculator compares them, via the reverse-engineered value-adjustment algorithm (`core.scoring.ktc_adjust`, a faithful port of keeptradecut.com's client-side logic, pinned by §11.11 to 13 live calculator trades captured 2026-07-27). Per side, assets sorted `v` desc, each contributes `(0.05·(v/C)^1.3 + 0.05·(v/(1.05·R))^6 + 0.1)·v` — `C` = top overall KTC value + 80, `R` = largest asset in the whole trade, both computed from the snapshot; a side's 2nd/3rd/4th+ assets below `R/2` take ×0.85/0.70/0.60 haircuts. The per-side sums are mapped back to value space with KTC's exact iterative inverse and the concentrated side is topped up so the final adjusted gap equals KTC's deserved gap. Require `|adjTotal(give) − adjTotal(get)| ≤ max(500, 0.20 · max adjusted side)` — band tolerances stay the league-measured ones. The fitted consolidation coefficients `c = (1.00, 0.90, 0.80)` are retired: they approximated this algorithm, and the adjustment provably does NOT cancel in roster-neutral pairs (≈ +3,377 for {8000, 2000} over {5000, 5000} at equal raw totals — "Value adjustments dont cancel out").
2. **Anti-fleece cap.** Raw `Σv` ratio ≤ **1.35**. Never exempted: fleeces don't clear, and reputation is an asset in an 11-opponent repeated game.
3. **Legality.** Both post-trade rosters legal: positional minima, roster caps with taxi routing per the taxi mechanics (§8), IR rules, trade deadline week 11.

**Enumeration policy (v3.3 — no pruning before pairing):** the engine keeps EVERY in-band, fleece-clean, legality-clean package variant (deduped by asset multiset) — v3.1's "one fairest get per give" pruning starved the pair matcher and is retired ("our pair and prune logic is severely broken"). Selectivity moves to the user's **target return range** (§5; v3.3.1 — min/max over the presets). The band remains a hard per-leg cap; the band-edge ceiling and the +8% anchor-ask convention remain card annotations. `W_min` retires as a gate (kept only as a display-level noise note in the CLI).

## 4. Targeting & market constraints (v5 — one vocabulary, three sources)

**Posture** is classified from **observed trades only**, over the trailing 12 months:

```
For each team: count completed trades where net flow = players in / picks out ("bought"),
and the reverse ("sold"). BUYER if bought ≥ sold+1 and bought ≥ 2 · SELLER mirrored ·
else NEUTRAL. Inactive (< 2 trades) ⇒ NEUTRAL.
```

Each label is displayed **with its evidence** and is user-overridable per team (`posture-overrides`).

**v5: every targeting fact is a CONSTRAINT in one machine-executable vocabulary**, applied by the spread finder (§4a):

```
constraint = { who: <username> | "me" | "*",
               side: "receives" | "sends",
               what: {class: "pick"|"player"} | {pos: "QB"|"RB"|"WR"|"TE"} | {asset: <name|key>},
               with: <username> | null,          # optional: only vs this counterparty
               mode: "require" | "exclude" | "prefer" }
```

- `require` — every leg involving `who` must match (hard). `exclude` — no leg may match (hard). `prefer` — matching pairs are tagged ★ and can be toggled to only-preferred; never reorders slider math (soft).
- Semantics are per-leg: `who receives what` constrains the package flowing TO `who` on any leg they are party to. `who = "*"` means every counterparty; `me` is my own side.

**Three sources, strict precedence (later wins per-team):**
1. **Posture defaults** (auto-compiled): BUYER → `{who: X, side: "receives", what: {class: "player"}, mode: "require"}`; SELLER → same with `class: "pick"`; NEUTRAL → no constraint. (This subsumes v3.3's posture-as-hard-constraint — identical behavior when nothing else is said.)
2. **Market intel** (`market-intel`, the skill's protocol): WANT → require on their receive side; DONT_WANT → exclude on their receive side; OFFERED(asset) → prefer on MY receive side vs that team; REJECTED → exclude of that exact shape; NOTE → no compilation. Active intel auto-applies; each item is individually revocable.
3. **Query constraints** (ad-hoc, per §4a call) — override both for the teams/assets they name.

Compilation of the user's own examples: "ronak wants draft picks" → `{ronakpatel32, receives, class:pick, require}` · "joey wants a running back" → `{joeydavis299, receives, pos:RB, require}` · "nobody wants stefon diggs" → `{*, receives, asset:Stefon Diggs, exclude}` (equivalently: Diggs is protected — never leaves my roster) · "josh b wants joe burrow" → `{josbaski, receives, asset:Joe Burrow, require}` · "colin is willing to trade away treveon henderson" → `{me, receives, asset:TreVeyon Henderson, with: cmgaither43, prefer}`.

- **Aim at visible holes** (carried): per-position starting-lineup sums annotate *which* players to offer — information, never a score term.
- **Two offers to the same team are noted** (carried) — appetite is psychology, which stays with the user.

## 4a. The spread finder (v5) — deterministic constrained search with three sliders

The interactive query engine behind the trade-negotiator skill (and the CLI `find` command). The legal spread space runs to millions; the finder makes constrained lookups and constraint-ADDING cheap:

- **Leg cache.** Per snapshot, the per-team package lists (give-lists × asset metadata: keys, classes, positions, Σv, count signatures) and my starter index are computed once and disk-cached under `.cache/` keyed by (snapshot fingerprint, params hash). Cold build is a one-time cost; every subsequent query — including re-queries with added constraints — loads warm and re-enumerates only the CONSTRAINED subsets. Warm and cold results are byte-identical (§11.12).
- **Query pipeline (deterministic):** compile constraints (§4) → filter each side's candidate packages BEFORE gate work → enumerate surviving legs per counterparty (exact §3 gate: band, fleece, legality) → cross buy×sell (asset-disjoint, distinct counterparties, count-neutral 0/0) → exact combined coordinates per §2 (incremental starter evaluator) → slider filter/sort → top `finder_top` (20) with honest counts. Constrained crossings small enough to finish exhaustively report EXACT counts; anything hitting `finder_cross_budget` saturates to verified floors (§5 doctrine). Favor bounds push down to LEG level before the crossing (v5.0.1: pair `min ≥ m` ⟺ both legs ≥ m, pair `max ≤ M` ⟺ both legs ≤ M — favor is a per-leg quantity, so the decomposition is exact), and a favor-banded query is exhaustive whenever the filtered crossing fits the budget. Numeric-δ walks order the crossing by the per-leg δ-score heuristic `leg_ΔW(δ) = iso_ΔS + δ·(ΔF_leg − iso_ΔS)` rather than the isolation floor; combined ΔS stays non-additive, so that order remains a disclosed heuristic — truncated δ-view counts are floors, never certificates.

**Sound crossing bound (v5.1) — the robust/floor objective is now COMPLETE, not heuristic.** Through v5.0.1 the floor-objective walks ordered and pruned on each leg's ISOLATION floor, `min(ΔS_leg, ΔF_leg) − r·Σsent_leg`, implicitly treating the pair floor as additive. It is not — ΔS is jointly determined by both legs through the lineup — so pairs whose legs are individually weak but complementary were pruned unseen. Measured on a simulated roster state: a robust favor-banded query returned **0 matches** where an exhaustive crossing of the same state held **4,157,460 verdict-true pairs, 88,911 of them clearing the query's own 1% bar** (best 3.00% return, floor +439; its buy leg shipped a starter and scored terribly alone). v5.1 replaces the key with

```
u(leg) = ΔF(leg) − r · Σsent(leg)          [prune when u_buy + u_sell < 0]
```

which is SOUND: `ΔF` is exactly additive across legs (§11.1 face conservation) and `floor = min(ΔS, ΔF) ≤ ΔF`, so `u_buy + u_sell < 0 ⟹ ΔF_pair < r·sent_pair ⟹ floor_pair < r·sent_pair ⟹ return < r`. The bound can never discard a qualifying pair. The walks test it in SPLIT form (`(r·sent_b − ΔF_b) + (r·sent_s − ΔF_s) ≤ 0`), which disagrees with the pair form on exact float ties — reachable, since ΔF and Σsent are integral and `r` is often round — so every walk carries a one-sided tolerance `XTOL = 1e-6` KTC points that keeps the boundary; the complementary below-walks apply the same tolerance with the same sign, so the two still partition the crossing space exactly. Consequences: a floor-objective walk that runs to completion is **EXACT** — its counts are provable and "no spread matched" is a real answer, not "none where I looked"; only budget-truncated walks remain verified floors. **Scope (v5.1, honest reading):** exact means exact over the POOLED legs. §5's per-signature variant pre-ranking (`variants_per_signature` gets by isolation floor out of the first `variant_scan_cap` gate-passers) is the same additivity fallacy applied to leg SELECTION, and the sound bound does not repair it — measured on the pinned scoped query, relaxing the caps to 6/12 exposes 829,914 further gate-clean pairs the default pool cannot represent at all. So "none exists" always means "none among the pooled legs", never a claim about the whole legal package space; every consumer sentence says so. Re-keying or widening the pool is a separate, unpriced change. Cost: `ΔF` typically runs 2–5× the floor, so the bound gives up later and visits more crossings per qualifying pair (measure per §11.10). The δ-view objective `ΔW(δ) = (1−δ)·ΔS + δ·ΔF` admits an analogous sound bound via `ΔS ≤ Σ face received` (also additive), but it is far looser; δ-views keep the disclosed heuristic until the robust runtime cost is known.
- **Slider 1 — δ (starter-friendly ↔ team-friendly):** view score `ΔW(δ) = ΔS + δ·(ΔF − ΔS)` and `return(δ) = ΔW(δ) ÷ Σ face sent`, δ presets 0 / 0.25 / 0.5 / 0.75 / 1 plus **robust** (default: v4 floor/verdict — good at every δ). Moving the slider is a labeled preference VIEW; §2's objective verdict is unchanged and always shown. Shape predicates are constraints, not sliders: `starter>team` ⟺ ΔS > ΔF, etc.
- **Slider 2 — total return:** threshold/sort on `return(δ)` at the selected δ (robust mode uses the guaranteed floor return). Presets as §5.
- **Slider 3 — counterparty favorability (KTC's own units):** per leg, `favor f = 100 · (adjTotal(they receive) − adjTotal(they give)) ÷ (adjTotal sum)` from the SAME §3 exact-adjusted totals the gate reads — the signed version of KTC's calculator equality metric, so `|f| ≤ 5` is literally "their calculator says FAIR at default variance", `f > 0` skews to them. Pair favorability = `min(f_buy, f_sell)` (the least-happy counterparty). Slider = floor on pair favorability, presets −10 / −5 / 0 / +2.5 / +5 / none; an optional ceiling stops giving edge away. The §3 band stays the hard outer bound — favorability selects WITHIN it.
- **Structural filters:** `--legs A+B` (one leg with A, the other with B), `--with X` (X on some leg), must-move / protected assets (sugar over require/exclude).
- **Efficiency contract:** adding a constraint NARROWS candidate sets — re-query cost is monotone non-increasing warm; slider changes never re-enumerate (coordinates and favor are stored per found spread; re-filter/re-sort is O(results)).

## 5. Pairings, the book, and execution

- **Target return (v4 numerator):** define `return(pair) = guaranteed floor ÷ Σ v(assets I send across both legs)` — the §2 worst-case gain, `min(ΔS, ΔF)` with ΔS combined across both legs, on face-value inventory deployed. The denominator stays face KTC (what the market prices). Legs are pre-ranked inside the pool by isolation floor as a disclosed heuristic; every STORED pair's coordinates are exact combined. Pure stored-value conversions have floor ≈ 0 and fall below the 1% stored universe automatically. **v5 — the board's dials are the finder's sliders (§4a), over stored inventory.** Three client-side controls: **δ selector** (robust default + presets 0/0.25/0.5/0.75/1 — re-scores stored pairs as `return(δ)` instantly from stored coordinates, labeled as a preference view), **min total return** (on `return(δ)`; robust mode = guaranteed-floor return; presets 1 / 2.5 / 5 / 10 / 20%, default 5), and **counterparty favorability floor** (replaces v3.4.1's raw-skim leg cap — the raw skim provably diverges from what the counterparty's calculator shows by up to 14 pts; presets −10 / −5 / 0 / +2.5 / +5 / no floor, applied to `min(f_buy, f_sell)` in §4a's exact KTC units). Sort: `return(δ)` desc, ceiling desc tie-break. Storage is **stratified by favorability bucket**: pairs bucket by `min(f_buy, f_sell)` over (−∞,−10), [−10,−5), [−5,0), [0,+5), [+5,∞); per bucket the nightly run keeps the UNION of top `pairs_per_band` (100) by robust floor-return, by ΔS, and by ΔF (deduped) — so both δ-slider extremes have inventory — plus per-bucket honest counts and a bucket × robust-return-band grid (`bands`: {lo, hi, stored, count, saturated, by_total}; **v5.1: a count is EXACT when its floor-objective walk ran to completion under the sound bound (§4a), and a verified floor only when the crossing budget truncated it** — `saturated` distinguishes the two, and the board discloses which). Each stored pair carries `coords`, `floor`/`ceiling`, `favor {buy, sell, min}`, and Σ sent, so every dial move is O(stored). Stored universe: robust floor-return ≥ 1%. Deep or constrained queries beyond stored inventory belong to the finder (§4a), not the board.
- **Posture is a hard constraint in the engine (v3.3):** the sell side of a pair must go to a **BUYER** (they receive players), the buy side must come from a **SELLER** (they receive picks); **NEUTRAL** counterparties accept either shape. Overrides (`posture-overrides`) apply before constraint evaluation. In the trade-negotiator skill the same constraints are qualitative — user intel can promote/demote a team's effective posture or exclude counterparties entirely.
- **The recommendation unit is the PAIR, fully count-neutral (v3.2, strict):** a **buy side** (I receive a player, paying picks — aimed at SELLER-posture counterparties) matched with a **sell side** (I send player(s) for picks — aimed at BUYERs), sharing no assets, and netting — for my side — **exactly `Δ(player count) = 0` AND `Δ(pick count) = 0`** ("completely neutral: we should end with the same amount of picks and same amount of players as before"). Players count wherever they land (active or taxi); picks count as picks regardless of year. No executed plan may inflate either inventory: the bundling wedge is harvested as value-per-slot upgrades at constant counts, never as asset-count accumulation. **Unpaired legs of any direction are building blocks, not executable recommendations** — sells and neutrals list in a labeled secondary section with their count deltas; buys with no exit sit on the watch list with the blocker named.
- **Ranking (v4 maximin; v3.4.1 filter):** pairs sort by TOTAL `return_pct` (guaranteed-floor return) descending within the user's filter (total floor + per-leg cap), ceiling desc as tie-break; every stored pair passes the §2 objective verdict (ΔS ≥ 0 AND ΔF ≥ 0) — posture fit is no longer a rank key because it is a hard pool constraint (§5 posture bullet); every leg individually passes §3. Pair cards carry an `overlaps` count (shared-asset conflicts against other stored pairs); unpaired-leg data keeps exact `exclusive_with`.
- **Execution protocol (rules, not math):** agreement-first — negotiate the buy to a verbal yes, execute the sell-leg, execute the buy minutes later (Sleeper trades process instantly, `trade_review_days = 0`). With open roster spots the buy may execute first; at the cap, sell first. Don't publicly fire-sale before making buy-side asks. After any executed trade, the whole board recomputes from fresh rosters.

Their side: **(ΔS +96, ΔF −191)** — a preference trade with breakeven **δ\* ≈ 0.3345**: a rational win-now manager (δ < 0.33) takes it, which is why the trade can close. ΔF is zero-sum (+191/−191, §11.1); ΔS is not (+191/+96) — deployment differs by roster, and that difference IS the arbitrage. Gate PASS. It is the fixture's only gate-clean 1-for-1 where my verdict is good with a three-digit guaranteed floor, which is exactly why §11.1 pins it.

## 11. Implementation invariants (the test suite)

1. **Face conservation:** on every leg, Σ face v leaving one side equals Σ face v arriving at the other, exactly — equivalently, `ΔF(side A) = −ΔF(side B)` on every leg. `ΔS` is per-side (deployment differs by roster) — a pinned example shows a pair where BOTH sides' verdicts are good.
2. **Independence regressions:** perturb every league-tab lineup parameter (`q_*`, `u_*`, replacement) and every roster count — no recommended pair's coordinates change. An uninvolved bench player moves neither `ΔS` nor `ΔF` of any trade. Grep-level: the trade path imports only the raw starter-sum solve, never the q/u/replacement machinery.
3. Fairness gate: a generated recommendation never violates the exact-adjusted band, the fleece cap, or legality; the §10.3 fleece shape is a pinned must-never-emit.
4. Posture labels reproduce deterministically from the transactions fixture; evidence lists match; override wins.
5. Recommended pairs net exactly zero players AND zero picks for my side (v3.2); a player-neutral but pick-inflating pair is a pinned must-never-emit; `exclusive_with` fires on shared assets.
6. Waiver backtests (Waller/Kyler) keep passing verbatim.
7. Zero-value (`unvalued`) players never contribute to `ΔW` silently — cards flag them.
8. Taxi/IR/deadline legality rules (§8) enforced on both rosters of every recommendation; taxi players are startable in `S` (promote-anytime) and otherwise count only in face, IR players in neither.
8b. **v4 coordinate pins:** (a) the two §2 QB cases produce (−1,000, +1,000) → NOT objectively good with breakeven δ* = 0.5 exactly, and (0, +1,000) → good with floor 0; (b) a non-starter sold for a same-face pick has floor ≈ 0 and never enters the stored board (the reclassification exploit stays dead, parameter-free); (c) interval endpoints are the δ-extremes: `ΔW(0) = ΔS` and `ΔW(1) = ΔF` for arbitrary fixture trades; (d) every stored pair satisfies `ΔS ≥ 0 AND ΔF ≥ 0` (one strict) — a verdict-violating pair is a must-never-emit; (e) stored order is maximin: floor desc, ceiling desc, id.
9. Determinism: identical snapshot ⇒ identical board, byte-for-byte.
10. Full nightly recompute within the v1 Lambda budget — the raw starter-sum solve enters the trade path (v3.4) via an incremental exact evaluator (asserted equal to a full re-solve over the fixture rosters and seeded random deltas), and the exact KTC gate runs behind a necessary-condition screen; the budgeted walks still saturate honestly, and under v3.4 every band count was a verified floor (§5) — **v5.1 supersedes that half**: a count is exact when its walk completes under the sound bound and a verified floor only when the budget truncates it (`saturated` says which; on the real nightly board it is still True everywhere, because ΔF's tail puts the affordable sound cutoff near 32% while storage starts at 1%).
13. **v5.1 soundness pins:** (a) the crossing bound never discards a qualifying pair — on a scoped fixture query the finder's matched set EQUALS an in-test brute-force crossing, element for element, and reports `exact=True`; (b) `floor ≤ ΔF` and `ΔF` additivity are asserted directly over fixture pairs (the two facts the bound rests on); (c) a constructed pair whose legs are individually below the return bar but whose COMBINED floor clears it is found by the finder (the regression that motivated the fix — pre-v5.1 it was pruned); (d) robust/board results may change vs v5.0.1 by ADDITION of previously-unreachable pairs — no pair that v5.0.1 returned may vanish for reasons other than being displaced from a top-N cut; (e) **boundary and phase integrity** — a crossing sitting EXACTLY on the bar (`ΔF_pair == r·sent_pair`) is kept by the top walk and excluded by the below-walk (the `XTOL` tie class, else the "never discards a qualifying pair" claim fails by one ULP), and the board's coverage phase hands a region back to the sound phase ONLY when that phase actually ran — the sound phase runs only where the crossing estimate proves it will complete (the estimate upper-bounds the walk's visits), because a phase that never enumerated a region must not own it: dropping an unwalked region loses storable pairs (measured on a starved walk: 487,795 crossings handed back, 49,709 storable), and the reverse would tally the same pair twice.
11. **KTC-adjust port regression:** the 13 captured calculator trades (2026-07-27 values, pinned as fixtures) reproduce integer-exact through `core.scoring.ktc_adjust`; a zero raw-adjustment gap short-circuits to S = 0.
12. **v5 finder pins:** (a) `favor` derives from the SAME adjusted totals as the gate (one source of truth) and `|f| ≤ 5 ⟺` the port's `check_equality` at variance 5; (b) constraint soundness — no returned spread violates any require/exclude, pinned on the §4 example compilation (ronak/joey/Diggs/Burrow/Henderson) against fixtures; (c) δ-view identities — ranking by `return(δ)` at δ=0 and δ=1 equals ranking by ΔS-return and ΔF-return; robust mode reproduces v4 maximin exactly; (d) finder determinism — warm-cache and cold-cache results byte-identical; identical query → identical results; (e) honest coverage — exhaustively-crossed queries report exact counts, budget-saturated ones report floors, never estimates; (f) posture-compiled defaults reproduce v3.3 `posture_allows` behavior when no intel/query constraint names the team; (g) board buckets are favor_min bands and every stored pair still passes the §2 verdict.

## 12. Changelog

- **v5.1 (2026-08-01):** the pair-crossing prune became SOUND for the floor/robust objective. v5.0.1 fixed *where* the walk looks for δ-views but left the floor objective ordering and pruning on each leg's ISOLATION floor, which implicitly treats the pair floor as additive. It is not — ΔS is jointly determined by both legs through the lineup — so pairs whose legs are individually weak but complementary were pruned unseen: a robust favor-banded query returned **0** where an exhaustive crossing of the same state held 4,157,460 verdict-true pairs, 88,911 clearing its own 1% bar (best 3.00%, floor +439; its buy leg shipped a starter, scoring terribly alone). Fix: key the walk on `ΔF − r·Σsent`, which is exactly additive and bounds the floor from above, so the prune can never discard a qualifying pair. Completed floor-objective walks are now EXACT (provable counts; "no spread matched" means none exists); truncated ones remain verified floors. Affects robust queries and the nightly board; δ-views keep the disclosed heuristic pending runtime measurement. Prompted by the user's challenge to the "market dries up" readings: "every trade that we make is roster-neutral… new trade opportunities should be popping up as our roster changes."
- **v5.0.1 (2026-07-31):** finder search-coverage fix. The v5.0 walk crossed the FULL pool in isolation-floor order under the crossing budget, but a favorability window concentrates the qualifying pairs exactly where isolation floors are small or NEGATIVE (fair legs have tiny face edges; floor = min(ΔS, ΔF)) — a δ-view favor-banded query returned 0 while an exhaustive check of the same pool found 3.1M qualifying pairs: the floor-ordered walk pruned the fair region by budget exhaustion, not by any verdict. Fix: (a) favor bounds push down to leg level before the crossing (exact decomposition — favor is per-leg), so favor-banded queries typically finish exhaustively and report exact counts (with a window set, the reported leg counts are the favor-eligible legs); (b) numeric-δ queries order the walk by the per-leg δ-score `leg_ΔW(δ)` instead of the isolation floor, so truncation fronts what the view ranks — non-certifiability doctrine unchanged; (c) the CLI/skill "no spreads" message now states whether the constrained space was exhausted (exact) or budget-truncated (a floor, not proof of absence).
